# 情报分析的时延曲线（原型）

**问题**：情报深度分析一次调用读 N 篇正文，墙钟随什么涨？是读输入慢（prefill）、还是输出跟着变长、还是长上下文下解码变慢？这决定了「拆成多次并行短调用」有没有用。

## 跑

```bash
cd services/meridian-ai-worker && pnpm wrangler dev --port 8787   # 不要加 --remote
cd apps/backend/prototypes/intel-latency && pnpm install --ignore-workspace
pnpm run sweep      # 主曲线：n = 5/10/20/30/45/60/81，每点 ≥2 次
pnpm run prefill    # 探针 C：max_tokens 压到 200，隔离 prefill
pnpm run crosscheck # 打真端点 analyze-single-story 交叉核对
```

数据来自 `../_data/fixture-F2.jsonl` 的簇 2（81 篇尼泊尔洪灾），正文从 R2 拉取后缓存在 `.cache/`。
按发布时间等距取样、两端锚定（复刻 `pickSpreadArticles`），保证各规模覆盖同样的时间跨度。

## 结论（2026-09-05，20 次主曲线 + 两个隔离探针）

**输出量主导，输入不驱动时延。**

```
corr(墙钟, 输入token) = +0.014      corr(墙钟, 输出token) = +0.848
prefill 斜率 0.207 秒/1k 输入 token → 全部 81 篇（67.9k token）只要约 14 秒
固定输出长度后，输入 7.5k → 67.9k，墙钟不升反微降（解码速度不随上下文下降）
```

最硬的一条：n=10（7.5k 输入）打满输出那三次是 119.6 / 132.0 / 136.9 秒，而 n=60（48.3k 输入，6.4 倍）不打满的四次是 38.1–56.9 秒。

**输出是双峰的，不是随输入线性涨**：正常收尾 2.2–4.7k token，或复读退化冲到 8192 并 `finish_reason=length`（20 次里 6 次，30%，与篇数无关）。解析失败 40%（6 次复读 + 2 次 JSON 引号未转义）。

**多喂材料没换来更多信息**：`corr(timeline条目, 篇数) = −0.015`。10 篇给 9–11 条时间线 / 10–13 个实体，81 篇给 12 条 / 12 个。

**两条旧结论被推翻**：生产记录的「91 篇 → 300 秒超时硬失败 / 67 篇打成 HTTP 500」复现不了（81 篇三次跑 58.3 / 76.9 / 122.0 秒，20 次调用零超时零 500）；30 篇那个 cap 的理由因此站不住。

**方法学**：同 prompt 同输出量下墙钟能差 7 倍（19.0 / 52.1 / 134.3 秒），这个后端上任何单次时延读数都不可信，至少跑 2–3 次取中位。
