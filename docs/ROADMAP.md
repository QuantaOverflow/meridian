## P1 · 情报分析层：信息利用率与输出退化

**业务价值：** 这一层产出的报告是简报的唯一材料来源，也是忠实度检查的「真相源」。它现在有两个已量化的病。

**病一：多喂材料不产生更多信息。** 2026-09-05 实测（`apps/backend/prototypes/intel-latency/`）：

```
corr(报告时间线条目数, 输入篇数) = −0.015
10 篇 → 时间线 9–11 条 / 实体 10–13 个
81 篇 → 时间线 12 条 / 实体 12 个
```

同一篇数内的方差（n=20 的实体数 8 vs 25）比跨篇数的差异还大。这解释了旧记录里「50 篇相对 30 篇在任何测得的轴上都没有收益」——**不是 50 篇不够多，是一次调用产出的信息量与输入量无关**。

**病二：输出复读退化 30%。** 同批实测 20 次调用里 6 次冲到 `maxTokens: 8192` 并 `finish_reason=length`，与篇数无关；解析失败率 40%（6 次复读 + 2 次 JSON 引号未转义）。生产靠 `INTEL_PARSE_MAX_ATTEMPTS=4` 重采样兜住成功率，但每次失败烧 8192 token + 100–200 秒。

**同时推翻的旧结论：**「91 篇 → 300 秒超时硬失败 / 67 篇打成 HTTP 500」复现不了（81 篇三次跑 58/77/122 秒，20 次调用零超时零 500）。`corr(墙钟, 输入token) = +0.014` 而 `corr(墙钟, 输出token) = +0.848`，全部 81 篇的 prefill 只要约 14 秒。**所以「拆输入降时延」这条路作废**，30 篇 cap 的原始理由也站不住（但保留它无损失——见病一）。

**要做（按成本升序）：**
1. **治复读退化**（一天内，收益确定）：降 `maxTokens`（复读更早停、重试更快）、prompt 禁止前置 Markdown 分析、或强制先吐 JSON。它同时吃掉时延和 40% 的解析失败
2. **砍掉没人消费的字段**：`contradictions`（跨文档两两比对，一次顺读做不了，且**写作层一次都没读过**）、`sources`（含 reliabilityLevel/bias，同样无消费）、`storyStatus`（只在 schema 里）。它们占着输出 token 一路顶到上限然后被丢弃
3. **修两个渲染标题错位**：`informationGaps` 被渲染成「## 影响评估」、`significance` 被渲染成「## 前景展望」——写作层看到的语义标签是错的
4. **分解成 micro-pipeline**（大改）：逐批抽取（并行）→ 代码归并（时间线排序、实体规范化）→ 矛盾检测（代码筛候选 + LLM 逐对确认）→ 综合（1 次短调用，只读结构化骨架不读原文）→ 信息缺口（代码算）。**验收指标是「多喂材料能换来更多信息」**（现在这条曲线是平的，拆开后应该是涨的），不是「更快」。调用量这一层翻 8 倍、整条管线翻一倍多

**前置：** 第 4 项需要**逐字段质量基线**——R2 里有现成的几十期报告，抽 5–8 份人读，看时间线/实体/矛盾/缺口各自的正确率与覆盖度。没有基线只能证明「不一样」，不能证明「更好」。

**逐 claim 判官的结构盲区**：对「方向反转 / 身份张冠李戴」召回 ≈ 0（理由里引用了矛盾却仍判 supported），跨家族换 llama 没救。因此 2026-08-29 那个「b′ 忠实度 +6.4pp」的结论作废。
