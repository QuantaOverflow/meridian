# ADR 0006：冷启动阶段怎么演化架构，以及尺什么时候必须重定

- 状态：已采纳（方法论；配套实现已入库：`eval/cluster-to-brief/CONTRACTS.md` 与 dataset / policy / judges 三层）
- 日期：2026-09-20
- 相关：ADR 0003（一簇即一条）、ADR 0004（写作层 v3）

## 背景：这一轮发生了什么

`cluster-to-brief` 这条线从 2026-09 起做架构搜索：先定了一把粗尺（判定包 + 判官 + 通过线
「致命错 0、硬错 ≤1、核心层覆盖 ≥2/3」），在 7 个按难度手挑的簇上比较各个候选臂，
连着演化了四代（v1 → v6）。

到 2026-09-20 做了两件之前没做的事，结论翻了：

1. **把成稿摆给读者读**。用户的判定是：原型像「结构化信息汇编」，生产那版信息少但是「高管简报」，
   他要后者。而通过线里的覆盖率恰恰在奖励前者——v4、v5 两代的加长与「必写」改动，
   是朝一条与读者价值相反的线在优化。
2. **在不挑选的真实一天上跑**（25 簇 818 篇，k=3）。逐句核对后：读者可见的错 6.5%、
   出处挂错 22%、39% 的简报有读者可见错或混写。此前在 7 簇上从没量准过。

同时暴露两个方法问题：判官没和人工对齐，把缺陷数虚高 4 倍；同一配置每次跑结果不同，
而我拿单次运行下过好几轮结论，有一次把因果归到了错的改动上。

## 争议：先有尺还是先看数据

社区实践（Hamel Husain 那套错误分析优先）默认「已经有一个在跑的系统，去看它的输出」。
本项目的反驳是：冷启动阶段要在**多个架构**之间选择，没有共同的尺就没法比，
所以必须先有粗尺——这不是鸡生蛋问题，而是两个阶段的不同需求。

两边都对一半。真正的缺口不是「先后顺序」，而是**尺被当成常量、四代没有重新校准**。

## 决定

### 1. 阶段划分与各自的尺

| 阶段 | 判据是什么 | 样本 | 结论能说什么 |
|---|---|---|---|
| 0 还没有输出 | **输出契约**（可判定：schema、逐句出处、篇幅）+ 用户读两篇 | 任意 | 只能说「能不能跑通」 |
| 1 架构搜索 | 粗尺，只用来**排序** | 手挑集合（难例密度高，跑得快） | 「哪个方向更有希望」 |
| 2 有了第一个端到端候选 | 由**真实分布上的错误分析**重新推导的尺 | 不挑选的一整天，分层 | 「能不能上线」 |
| 3 上线后 | 生产流量即数据集 | 每日 | 回归与漂移 |

**阶段 0 最值钱的决定是输出契约，不是指标。**「每句带出处」让杂质率、数字核对、引语核对、
出处可解析全部变成零 LLM 的机械判据；生产那条链路没有出处，今天想量都量不了。

### 2. 尺的有效期

**粗尺只对一代架构有效。** 每演化一代，必须拿当代候选在真实分布上跑一次、做错误分析，
用观察到的失败模式校准尺。这一轮跑了四代没校准，代价是两代在错方向上优化。

「实现层中途不得改判据」（CONTEXT.md）防的是比较过程中偷换标准，**不等于判据永远不改**。
要改就开新一轮、旧读数作废——这已有机械形态（判定包指纹）。

### 3. 指标必须与读者价值对一次

成本最低的校准方式是把两份成稿摆给用户读，几分钟、零 API 成本。
比跑更多轮、算更多指标都便宜。这一轮拖到第四代才做。

### 4. 判据只描述输出性质

判据里不得出现结构词（块数、step、窗口、调用次数）：

- ❌ `requireSplitOrReject：必须拆 ≥2 块` —— 假定多块架构，架构一改就失效（本轮实际发生）
- ✅ `noEventMixing：每个块引用的文章必须落在同一个事件组内` —— 一块、多块、判不可写都适用

实测：同一条 `noEventMixing`，v1 的五块输出与 v6 的一块输出能在同一张表里比较。

### 5. 四层边界（借 Inspect 的概念，不引入框架）

dataset / solver / scorer / judge 互不依赖，细则见 `eval/cluster-to-brief/CONTRACTS.md`：

- dataset 定在最宽的稳定边界（一天全量 + 聚类快照 + 选中列表），标注挂在**输入**上；
- 输出契约架构中立，带逐句出处与原句原文（`quote`），scorer 因此不依赖生产的切句逻辑；
- scorer 只出事实，通过线单独放 `policy.json`，改通过线不作废历史读数；
- **评分与生成分离**：scorer 只读已落盘产物，判据变了不必重新生成（抄自 Inspect 的 offline scoring）。

不引入 Inspect 本身的理由：判官是 Claude Code 的 subagent（零 API 费），
生成侧全在 JS，引框架只换个壳。**判官准不准、判据定成什么，框架本来也不负责**——而这两件正是本轮的损失。

### 6. 判官与方差

- 判官进对比表前，先在 ≥30 条人工标注上量真阳率/真阴率；没量过的只能当量级参考。
- 每轴一个二元判官，**证据范围写死**：`citation-support` 只读被引的那句，其余轴必须读全簇。
  混了就会把同一个缺陷数两遍（本轮 4 倍虚高的根因）。
- 派判官必须过落盘验收（文件、schema、覆盖、promptId），不过就不采用。
- 默认 k=3，报均值与极差；单次结果标成假设。

## 已证伪 / 已废弃

- **「7 簇手挑集合的比例可以外推」** —— 难例占一大半，真实分布里这类占三分之一。
- **「覆盖率代表质量」** —— 它奖励枚举，且概括写法会被判成漏写。
- **「prompt 能压住编造关系」** —— 明确禁止后，三次运行仍各有出现。
- **「结构型判据」** —— 见上。

## 未决

- 读者可见的 6.5% 怎么降：下一个单变量实验是换写作模型（同一 dataset、同一批对齐过的判官）。
- 22% 的出处挂错：把机械补出处从数字/引语扩到专名与从句。
- 路由门拒掉的 32% 里那些真实小故事怎么捞回来：属上游事件分离，另开。
