# ADR 0011：运维台——只读、只看生产运行、只管流水线健康

- 状态：已采纳，2026-10-06 上线（backend `57951f91`、ai-worker `89b18c53`、ml-service `8e021836`、Pages 提交 `d176c2f`）。
  ADR 0012 决定 8 给决定 5 加了两条判据（逐句核查的 key 被拒 → 红，回退超过五分之一 → 黄，看最近一次生产运行），
  给决定 6 加了一笔不在 Cloudflare 账单里的花费（DashScope，按美元单列，算生产占比时先减掉）
- 日期：2026-10-06
- 相关：`packages/contracts/src/ops-console.ts`（接口形状）、`apps/backend/src/lib/ops/`（读数与判据）、
  `apps/frontend/src/pages/admin/`（页面）、`scripts/deploy.sh`（部署带上提交信息）；术语在 `GLOSSARY.md`「运维台」；
  spec 与票在本地 `.scratch/ops-console/`（不入库，本文是它们的入库结论）

## 背景

流水线有没有好好干活，原先要分别去查 Neon、R2、Cloudflare dashboard 和一个只管来源的后台页。几件事因此很久没人发现：
模型 key 失效后流水线静默停了 12 天；ml-service 连续五天跑旧镜像而运行状态全是 COMPLETED；
77% 的正文黏成一行；一个账期第二天就花到 $32，几乎全是开发试验。

## 决定

1. **回答四个问题**：今天这期正常吗、哪里出了问题、是不是在变差、有没有来源在掉。五个视图：
   Health（`/admin`）、Trends、Cost、Sources、单次运行详情（到每次模型调用的原始请求与回复）。
2. **只读**。不放重跑、撤回、重处理的按钮；来源的暂停 / 恢复留在单个来源页。
3. **只管流水线健康，不判成稿质量**。一事多块、不值得上这类检测器要先在已标注的数据上量过准确率，另立项。
4. **只算生产运行**（定时触发的那次）。手动运行不进任何读数。
5. **判据集中在 backend，阈值是命名常量**（`lib/ops/run-rows.ts`、`source-status.ts`、`health.ts`），前端只展示。
   - 今天这期红：失败、没选出新闻、北京时间 22:00 还没跑完。黄：降级、比基线慢或贵 1.5 倍以上、
     近 24 小时超过 20% 的正文黏成一行、生产 Worker 有报错、ml-service 不健康。
   - **判慢 / 贵的基线从 `BASELINE_START`（2026-10-05，写作–核查循环上线）起算，不足 5 次不判。**
     循环让一期从约 17 分钟、两三千 neurons 变成约 30 分钟、八万多 neurons；拿上线前的运行当基线，之后每期都会被标黄。
     以后再有让正常耗时或成本整体换档的改动，把这个日期往后挪。
   - 来源分六种，先匹配的赢：暂停（灰，不算异常）、没在抓（红，两个抓取间隔没有一轮成功）、死 feed（红）、
     正文抓不下来（黄，>30%）、正文格式不对（黄，垃圾页或黏成一行 >20%）、正常。
6. **花费只把模型用量换成美元**：按 Cloudflare 的计费周期（4 号到次月 3 号，UTC），扣掉 10,000 neurons × 周期天数的免费池，
   $0.011 / 千 neurons。其它计费项只显示占免费额度的比例。账户合计（对账单用）与生产占比分开显示。不设预算线。
7. **给人看的日子一律是北京日**。Cloudflare 的数据按小时取再归到北京日；**账期的合计仍按 Cloudflare 的 UTC 周期算**，
   与发票同一口径，所以每日用量图的第一根柱子只有 16 小时。
8. **Cloudflare 读不到时，对应面板写出原因，接口照常回 200**，不显示成空（空会被读成「没问题」）。
9. **页面要的数在写入时就算好**：run 结束时把调用数、neurons、各步耗时、块与核查计数、降级原因写进
   `brief_runs.ops_summary`；抓取成功时记正文行数（`articles.body_lines`）；抓取程序每轮把结局记到来源上
   （`sources.last_attempt_at` / `last_error`）。页面不在打开时去 R2 逐条加。
10. **各服务自己报版本，不跟 GitHub 比**。三个 Worker 一律用 `scripts/deploy.sh` 部署，它把提交短哈希、标题、
    是否有未提交改动带上去。「本地提交没上线」的提醒放在 pre-push（只提醒不拦）。
11. **后台接口的登录门挡在一处**：`/api/admin/` 下除登录外，没有会话一律 401；测试按文件树逐条验，新增接口不用改测试。

## 替换了什么

- 原来的 Source Analytics 页并进 Sources 视图；backend 的 `GET /admin/sources` 与它的查询删除。
- 没有调用方、也不认 DEGRADED 的两个聚合端点 `GET /observability/trends`、`/observability/health/summary` 删除。

## 后果与已知代价

- **`lastChecked` 只在整轮成功时前进**，所以「没在抓」包含两种：抓取程序没去、去了但失败。后者现在会写出原因。
  上线当晚就用上了：CBS News World 的 feed 对 Cloudflare 出口回 `406 Not Acceptable`，同一地址从别处抓是 200；
  给请求加 `Accept` 头没有治好，是按请求来源在拦。怎么处理未定。
- **待处理清单会合并**：同一种来源问题有 3 个及以上（黄的 2 个及以上）时合成一行，免得抓取程序整体停了时把清单占满。
- **ml-service 每次部署都要重建并推送整个镜像**：提交信息是作为构建参数进镜像的。从本机推镜像不稳
  （`registry.cloudflare.com` 经本地代理会超时），上线那次重试三轮才过。
- **读 ml-service 的健康会唤醒它的容器约 10 分钟**：Health 页只在打开时请求一次、不轮询；pre-push 的提醒也会问一次。
- **backend 多了一个必填 secret `CF_ANALYTICS_TOKEN`**（Account Analytics: Read）。要在交互式终端里设：
  经非交互的 shell 管道执行 `wrangler secret put` 会存进空值，表现是面板全写「token 未设置」。
- 回填出来的历史运行没有降级原因（当时只进了日志）。

## 上线时对过的读数

- 上个账期（9 月 4 日 – 10 月 3 日）：2,978,178 neurons、免费池 300,000、$29.46，与账单一致。
- 生产 Worker 报错：14 天 0 次。
- 2026-10-05 那期（循环上线后第一期）：393 次调用、86,052 neurons、$0.947；25 块，20 块无问题、5 块经改写修正、0 块带未核查句子。

## 没验证的

- workflow 里写汇总的那一步、抓取时写正文行数的那一行，上线时都还没在真实运行里执行过（要等上线后第一期）。
- 页面只由所有者本人在浏览器里看过；手机宽度没人系统看过。
