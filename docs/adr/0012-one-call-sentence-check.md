# ADR 0012：逐句核查改成「代码取证据 + 一次调用」，模型换 DashScope 的 qwen3.8-flash

- 状态：已采纳（2026-10-06），代码已合入、**未上线**：生产配置仍是 `BRIEF_CHECK_MODE = "agent"`，切换等用户补好 key 与网关后再定
- 日期：2026-10-06
- 相关：ADR 0010（写作–核查循环，本文只换其中「逐句核查」这一步）、ADR 0011（运维台，本文给它加了两条判据和一笔花费）；
  用词见 `CONTEXT.md`「写作–核查循环」；原型在本地 `apps/backend/prototypes/writer-faithfulness/`（不入库，读数在其
  `out/ref/results.md` 2026-10-06 各节，本文是它的入库结论）；spec 与票在本地 `.scratch/one-call-sentence-check/`

## 背景

写作–核查循环 2026-10-05 上线，首期（25 块、87 句）花 $0.94，其中逐句核查 $0.71，占四分之三：

- 每句一个 qwen3.8 agent，平均 3 次调用，每次都把提示词和此前的对话整段重发；
- 94 个 agent 里 87 个的结论是「没问题」，九成以上的钱花在确认本来就没问题的句子上。

目标是把循环新增的成本降约 90%，质量不退。完成时间不在这次目标内。

## 决定

1. **逐句核查不再是 agent。** 每句成稿由代码先取好证据，一次模型调用给结论。结论的形状不变（没问题，或问题 + 证据原句 + 建议改法），
   所以循环里核查之后的部分——意见消息、整块改写、只复核改过的句子、最多两轮、ADR 0010 决定 5 的降级规矩——一个字没动。
2. **证据由五条规则取**（`utils/evidence-pack.ts`，上限都是测出来的，别改）：
   1. 成稿引用的每一句，连同同一篇里前后各一句；
   2. 整句按词搜最像的 6 句（就是原来 agent 的 `search` 工具那套 idf 检索）；
   3. 每个分句各按词搜 8 句；分句在 `; : — –`、后面不跟数字的逗号、连接词处切，留三个词以上的；
   4. 整句按意思搜最近的 6 句，每个分句各 5 句；
   5. 句中每个计数（「57 人死亡」）在整簇里各次报道的时间线。
3. **按意思搜用 Workers AI 的 `@cf/baai/bge-m3`**：整簇每句的向量一块算一次，各句、各 epoch、各轮改写共用。
   算不出来就只按词搜，块记录里记 `meaningSearch: false`，不算错。
4. **模型是 DashScope（阿里云百炼）的 `qwen3.8-flash`**，经 Cloudflare AI Gateway 的 custom provider，网关缓存关掉
   （同一句核查多个 epoch 要的是独立的几次回答）。只有这一步用 DashScope，标重点和写作仍在 Workers AI。
5. **回复先写核对过程、再给结论**（`CHECKS` / `RESULT` 两段）。核对过程不能省：让模型只写简短的对照行时，同一个模型抓到的错句少一半。
6. **失败就回退到原来的 agent，并留痕。** 一句的 DashScope 调用拿不到可用回复——key 无效、内容审核拒绝、限流 / 超时 / 5xx 重发用尽、
   或三次回复都读不出——这一句改由 qwen3.8 agent 核查，块记录里记一条（哪句、哪一轮、原因、厂商报错原文）。
   一块里第一次 key 无效之后，这一块余下的核查不再去 DashScope。agent 也没结论才算「没核到」，照 ADR 0010 处理。
7. **两个配置项**（ai-worker 的变量）：`BRIEF_CHECK_MODE` 取 `one_call` 或 `agent`，缺省或写错按 `agent` 并打 warn；
   `BRIEF_CHECK_EPOCHS` 含义不变，默认仍是 1，0 关掉核查。切回 `agent` 不用回滚代码，请求与改动前逐字相同。
8. **运维台**（修订 ADR 0011 决定 5、6）：
   - 最近一次生产运行有 key 被拒的回退 → 待处理清单红；回退超过核查次数的五分之一 → 黄（20% 是起步值，没量过）。
     都引用厂商的报错原文。看「最近一次」而不只看今天：每天 21:00 才跑，只看当天的话 key 过期每天只显示三小时。
   - 花费页多一项 DashScope：它不在 Cloudflare 的账单里，数来自各次运行的汇总，按美元单列；
     算「生产占 Cloudflare 用量的比例」时先把它减掉。块记录与运行汇总里的 neurons 含这笔钱（按 $0.011 / 千折算），另有美元分项。
   - 配成 `agent` 或关掉核查的运行，在运维台上和这次改动之前一样。

## 读数

**held-out 完整循环**（111–115 期 40 块，与 ADR 0010 同一份草稿配对；Opus 盲评，编码时不看臂；各跑一次）：

| | 确定走样句 | 39 块的核查花费 |
|---|---|---|
| v4-pro 单写（草稿） | 6/152 | — |
| 循环，qwen3.8 agent，核查 1 次（上线的做法） | 2/152 | $1.458 |
| 循环，一次调用，qwen3.8-flash，核查 1 次 | 2/152 | $0.111 |

一次调用那臂没有被判出改写新引入的问题；核查花费少 92%。这一臂用的是规则 1、2、5（较窄的取证），盲评只重判了它改动过的 10 块，
其余 28 块沿用 10-04 对同一份草稿的判定。

**取证加宽**（只跑核查，对照 10-04 的判定；qwen3.8-flash，各跑一次；抓到的错句 / 好句误报）：

| 取证 | dev-1（32 错 / 40 好） | dev-2（28 / 26） | held-out 6 句确定走样 | 每句 |
|---|---|---|---|---|
| 规则 1、2、5 | 29 / 2 | 24 / 2 | 4 | $0.0007 |
| 加规则 3 | 28 / 0 | 24 / 0 | 5 | $0.0008 |
| 再加规则 4（上线的配置） | 29 / 1 | 23 / 0 | 5 | $0.0008–0.0009 |
| qwen3.8 agent（两次运行） | 26、26 / 2、0 | 25、25 / 1、1 | 5（单次） | $0.0075（生产） |

- 规则 4 的来由：held-out 里唯一一句按词搜取不到证据的错（成稿写「始于 2015 年」，原文是「2014 年发起 Operation Inherent Resolve」），
  关键原句按词搜排第 90 位，用分句「began in 2015」按意思搜排第 5。agent 当初是拿第一次搜到的行动代号再搜一次才找到的。
- 加宽后 held-out 每次仍漏 1 句，但每次漏的不是同一句；那一句 agent 两次运行里也漏过一次。剩下的是单次结论会翻（约 10%，10-04 量过），
  不是代码取不到证据。
- v4-pro 的错句全部要靠引用之外的原文才看得出（held-out 6/6）；开发集的错句多出自较弱的写作模型，三分之二在引用的原句里就能看出。
  所以开发集会高估「只看引用句」的取证，判断要看 held-out。
- 证据包中位数 32 句、最多 72 句（held-out）；从 13 句加到 33 句，抓到的和误报的都没变。

**满负荷干跑**（2026-10-06，10-03 期 21 块，6 块在飞，本地 ai-worker 直连 DashScope，核查 1 次）：

| | agent（10-05 干跑） | 一次调用 |
|---|---|---|
| 块阶段花费 | $1.02 | $0.29 |
| 其中核查 | 约 $0.8 | $0.074（92 句、93 次调用） |
| 用时 | 8.8 分钟 | 4.1 分钟 |
| 写出 / 带没核到句子的块 / 回退 | 21 / 0 / — | 21 / 0 / 0 |

按 2026-10-05 那期推算，循环每天从约 $0.94 降到约 $0.32（约 −66%）。剩下的几乎全是 v4-pro 写作（约 $0.22），所以到不了 90%。

## 为什么代码取证能持平

10-04 的错误分析：agent 稳定漏掉的 12 句里 10 句是它已经找到矛盾的原句、又自己找理由放过。瓶颈在判断，不在查找。
一次调用保留了判断这一半和它写出来的推理，只把查找换成代码。便宜模型当 agent 不行，是多步协议（规划、守格式、不转圈）做不好，
不是不会比较两句话。

## 证伪清单（别再走）

- **给 agent 开前缀缓存**：qwen3.8-27b 经 binding 带 `x-session-affinity`，8 次重放 `cached_tokens` 全是 0，同一段对话的后续步也是 0。
- **一块一次调用**（所有句子一起核）：简短对照行抓 13/32、11/28；写出核对过程也只到 22、17。模型会在明显不同的两段话旁边写「一致」。
- **整簇原文全给**（约 128 句）：glm-4.7-flash 把 66 句好句标了 63 句；10-04 用 v4-pro 试，40 句好句误报 12 句。
- **Workers AI 上更便宜的模型做一次调用**：glm-4.7-flash 20/32、15/28 且误报多、8% 回复解析不出；gemma-4 21、15。都只抓到约六成。
- **glm-5.3-flash 做一次调用**：每次写 5,000 token，解析不出结论。
- **DashScope 的 qwen3.7-flash、qwen-flash**：抓到的一样多，误报是 qwen3.8-flash 的 2–6 倍；误报每次触发一次 v4-pro 改写。
- **换厂商不换模型**：同样的 qwen3.8-27b 在 DashScope 只便宜 20–30%。
- **按取证结果逐句决定走一次调用还是 agent**：规则 3、4 加上之后，66 句错句里没有剩下只有 agent 自己查才抓得到的；没做。
- **把写作那边的复读检测接到核查回复上**：逐部分核对本来就反复抄同一句原文，它在 152 条正常回复上误拒 10–11 条，
  满负荷干跑里表现为 94 次核查多用 9 次调用、1 句被迫回退。真的复读退化会写到 token 上限，由「被截断即读不出」接住。

## 已知风险与没验证的

- **上线的配置没有做过完整循环的盲评。** held-out 的循环读数是较窄的取证跑的；规则 3、4 只有「只核查」的读数和一次满负荷干跑。
- held-out 只有 6 句确定走样，各臂只跑一次；2 对 2 是持平，不能说哪个更好。这份 held-out 已经用了三次。
- **DashScope 的内容审核**：开发集 270 次调用里拒了 1 次（`DataInspectionFailed`），held-out 152 次与干跑 186 次里是 0。被拒的句子回退 agent。
- **厂商依赖**：2026-09-24 删掉 DashScope 是因为 key 失效让流水线静默停了 12 天。这次只有核查依赖它，失败有 agent 兜底，
  回退当天在运维台上看得到。key 失效那几天成本回到约 $0.94。
- key 失效时，一块草稿的几句是同时发出的，会各撞一次 401，之后的才跳过；失败的请求不花钱，只是多几条日志。
- DashScope 返回空正文时不重试，直接回退 agent。
- 按意思搜用的是 bge-m3，不是流水线里的 e5-small；向量调用的花费没计进块记录的 neurons（量很小，单价没查）。
- qwen3.8-flash 在 DashScope 的限流没查；一块 6 句同时发、6 块在飞时没见到 429。
- 生产并发下经 AI Gateway 的耗时没测；干跑是本机直连 DashScope。
- replay 还不认 DashScope 与向量这两类调用：`one_call` 模式的运行暂时不能整期重放。

## 后续

- 上线：用户建新的 DashScope key、确认网关（custom provider `dashscope`、关缓存）、放 secret，填好 `wrangler.toml` 里的网关地址，
  再把 `BRIEF_CHECK_MODE` 切到 `one_call`；首期跑完读运维台与调用日志。
- **agent 这条路是留着用的，不是待删的旧代码**（清死代码时别按「平时没人走」删）：它是 `BRIEF_CHECK_MODE` 的另一档，
  也是 `one_call` 下每一句的兜底，DashScope 一出故障就会走到。没有它，厂商故障那几天句子会不经核查发出去。
  退役它要同时满足两条，并由用户拍板：一次调用在生产上稳定跑过一段时间、回退很少；接受 DashScope 故障时句子按「没核到」发草稿。
  退役时一并删 `services/sentence-check.ts`、agent 的 prompt、`@cf/qwen/qwen3.8-27b` 与 `brief_block_v6_check` 这个 phase。
- 核查 2 次现在每天只多约 $0.08（ADR 0010 里 2 次那臂是 0/152），但没在一次调用上测过；上线一周后再定。
- 离 90% 还差的是写作：换写作模型是另一个决定，质量风险最大，本文不碰。
