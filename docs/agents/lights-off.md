# Lights-off：无人值守地跑出一个 PR

> 从 `CLAUDE.md` 按需指过来：用户说要 lights-off 地做一件事（「睡前启动、第二天看 PR」「自动完成后提 PR」）时读。
>
> 这套做法还在摸索，没有成熟到固化成 skill 或命令（用户 2026-10-07 定：先不做）。靠用户在对话里说出来触发；跑过几次再回来改这份文档。

## 是什么

用户不在场的时候，agent 自己把一件事做到出一个 PR；第二天用户读这个 PR。
**用途是预演**：把第二天想开发的新功能先跑一遍，看会撞到什么、做出来大概是什么样。能跑出可以直接上线的结果更好，但那是额外收获，不是指望。
「lights-off」借自 HumanLayer 的《Why Software Factories Fail》，那里指「没有人读代码、产出直接进生产」，结论是行不通。
本仓只借前半：**跑的时候没人盯；跑完人要读，PR 不直接合并。**

## 两个前提：目标对齐，结果有 back-pressure

自动化能不能成，取决于两头（用户 2026-10-07 定），中间交给 agent：

1. **目标意图对齐**——交出去之前，人和 agent 对「要什么」理解一致。靠 `grill-with-docs`，不省。
2. **结果验收（back-pressure）**——agent 每做一步，都有一个不靠它自己判断的信号告诉它对不对，错了就被顶回去重做。
   没有它，agent 会在一个错的改动上越盖越高，早上拿到的只是「它自己说做完了」。

back-pressure 在本仓指这些，越靠前越便宜、越靠后越接近真实：

- 类型检查、eslint、knip、路由对账、staging 隔离检查（`pnpm typecheck` 与 pre-push 里的那几项）。
- 测试：红绿循环里那条先红后绿的测试、golden 快照、replay。
- 真跑：Staging 运行的判定（`node scripts/staging-run.mjs`，红了非零退出）。
- **learning test**：对一个拿不准的前提（外部服务怎么表现、某段现有代码到底读不读某个东西），不靠读文档或读代码下结论，写一小段代码真去试一次。
  staging 那次「简报不读 R2 里的正文」就是读代码读错的，一次真跑才纠正过来。

每次 lights-off 启动前要说得出：这件事的 back-pressure 是哪几条命令，其中哪一条是最终的裁判。说不出，就不适合交出去。
给 agent 的检查输出要省上下文：过了只回一行，失败才给报错（本仓的 git hook 已经是这个写法，脚本里的 agent 照用同一批命令）。

机器判不了的仍然归人：LLM 成稿的质量、代码设计的好坏。这两样没有 back-pressure，所以 PR 不直接合并，第二天要读。

出处：HumanLayer 的 Kyle Mistele《Loop Engineering from First Principles》（把循环当控制系统：确定性的检查是传感器，agent 是执行器，人的反馈改的是控制器；小步增量，不堆 PR）
与 AI That Works #44《Agentic Backpressure Deep Dive》。两个都是视频，本文依据的是它们的文字摘要，没有看视频本体。

## 完成标准（用户 2026-10-07 定）

第二天有一个 PR，它属于下面两种之一：

1. **目标没做完，或做出来的是原型** → PR 要能给第二天的开发提供 insight：撞到了哪些事先不知道的事、哪些路走不通、哪些部分能留。
2. **目标已经做完** → 第二天在它的基础上优化代码与架构，拆成几个小 PR，review 后合并。

两种都不是「把这个 PR 合进主干」。

**交付的形状有两种，都可以**（用户 2026-10-07 补充）：

- 一个 PR。
- **一串增量的小 PR**：workflow 按小步做，每一步是一个小 PR，过了自己的 back-pressure 才做下一步。第二天用户按顺序读、按顺序合，省掉「先出一个大的、再回头拆」那一轮。
  活本身能切成先后几步时优先用这种（做法见下面「增量交付」）。

## 启动前的流程：目标先对齐，其余压在 30 分钟以内

workflow 启动后不能改计划、不能问人，所以凡是中途会需要人判断的，都挪到启动之前。

**目标清楚是杠杆最大的一步，这一步不省**（用户 2026-10-07 定）：目标不清楚就用 `grill-with-docs` 对齐到清楚为止，一次只问一个问题，花多久算多久。
用户希望介入尽量在 30 分钟以内，省的是别处：agent 把能自己做的都做完，给用户的每一样都压成一屏。目标本来就清楚时，下面六步约 25 分钟。

| 步骤 | agent 做什么 | 用户做什么 | 用户用时 |
|---|---|---|---|
| 1. 说目标 | — | 两三句话：要什么功能、为什么 | 2 分钟 |
| 2. 一屏简报 | 读代码，把事实查实（尤其「某某不需要」这类否定句；拿不准的写 learning test 真试一次），起草：目标、back-pressure 是哪几条命令与最终的裁判、最薄的那一条全链路、查实了的前提、不做什么 | 读一屏，不对就说 | 5 分钟 |
| 3. 对齐目标 | 简报里还有没定的：用 `grill-with-docs` 问，一次一个，带推荐答案；只问目标、用户能感受到的行为、花钱与授权，实现细节自己定。没有没定的就跳过 | 逐个答 | 目标清楚时约 8 分钟；不清楚时问到清楚为止，不设上限 |
| 4. 预检 | 把要走的流程空跑一遍（部署 staging、触发、push、开 PR），看哪里弹确认、被哪个钩子拦、缺哪个工具或密钥；确认 subagent 里也做得了。自己能解决的自己解决 | 只处理 agent 解决不了的（预先放行某类命令、在网页上点一下） | 5 分钟 |
| 5. 试跑第一阶段 | 只跑「打通最薄的一条并真跑」。未知多半在这里撞出来 | 不用守着；只有撞到要拍板的事才被叫回来 | 0–5 分钟 |
| 6. 过目脚本 | 一屏：分几个阶段、每阶段几个 agent 与模型、许做与不许做、花费与轮数上限、停下的条件、卡住时怎么办 | 扫一眼，说「开始」 | 3 分钟 |

目标清楚时合计约 25 分钟。第二天读 PR 的时间另算。

规矩：

- 时间从预检、试跑、过目脚本上省，不从对齐目标上省。目标没对齐就交出去，夜里跑出来的东西整个建在错的前提上。
- 不让用户读整份 spec：第 2 步的一屏简报加第 3 步的回答就是这次的 spec，agent 自己另存一份完整的供脚本里的 agent 读。
- grill 之后目标仍然说不清（要边做边看才知道要什么）：这件事今晚不适合交给 workflow，改用单个 agent 探路，或白天走 `docs/agents/dev-workflow.md` 的正常流程。
- 卡住时的默认规矩：只在不改变简报的前提下换路；要改简报里定过的东西就停下，把问题和可选的改法写进 PR。
- 授权范围写进简报：能建、能改哪些云上资源，能不能部署 staging、放密钥，花费与真跑轮数的上限；生产的 worker、库、bucket 一律不许碰。到上限就停，如实写进 PR。
- 会话要撑到早上：终端开着，电脑不睡眠。

## 预演不等于降低标准

预演的代码按生产代码的规范写，编排也要认真设计。理由：产出要么直接用，要么当第二天的依据——写得潦草的原型，撞出来的问题分不清是路不通还是写得差。

**编码规范**（和平时一样，不因为是预演放宽）：

- 先读相关的现有代码再动手；只改与目标有关的地方；照现有的写法与风格。
- 生产代码走 `tdd`：在定好的接缝上红绿循环，测行为不测调用关系，不 mock 内部函数。脚本不写测试。
- 用 `GLOSSARY.md` 里的词；碰到的目录有路径规则（`.claude/rules/`）就照它做。
- 提交过 pre-commit，不用 `--no-verify`；接口约定先写死并提交，再让别的 agent 依赖它。
- 派出去的每个 agent：显式传模型、写明不许再派、回报里如实列出没做到和没验证的。

**dynamic workflow 的脚本要按这件事设计**，不是把票并行一发了事（2026-10-07 staging 那次就是这样：5 个 agent 各写各的，约 1600 行全过测试却没碰到任何真实问题，原样留下的只有十几行）：

1. **先薄**：第一阶段一个 agent，打通最薄的一条全链路并真跑，失败就修再跑。未知在这里撞出来。
2. **约定写死**：第一阶段跑通后把接口约定定下来并提交，后面的阶段只读不改。
3. **再宽**：互不相干的部分才并行铺开，各用独立的 worktree。
4. **合起来真跑**：一个 agent 把全部并到一起，对着真实环境（如 Staging 运行）再跑一次。
5. **审查与修复**：一个 agent 独立审整份 diff，问题回给对应的 agent 修；轮数有上限。
6. **守住上限**：脚本里检查花费与轮数，到了就停并如实返回，不硬撑到「全绿」。


### 增量交付：夜里直接出一串小 PR

照 Kyle Mistele 的思路（小步增量、每步有传感器、不堆 PR），workflow 可以不攒成一个大 PR：

- **一步一个 PR**：第一个是打通最薄那一条的切片；之后每个只加一样东西，各自的 diff 只含自己那一步，大小以一次读得完为准（几百行以内）。
- **过了再走**：每一步先过它的 back-pressure（检查、测试，涉及整链路的再真跑），过了才提交、push、开 PR，然后才开始下一步。没过就修；修到轮数上限还没过，就停在这一步，后面的不做。
- **叠起来**：后一个分支从前一个分支开出，PR 的基底指向前一个分支，这样每个 PR 只显示自己的改动。合并顺序写在第一个 PR 里。前面的分支要返工、或主干变了要把这一串挪过去时，可以改写后带租约强推（写明远端和分支名）；主干分支与不带租约的强推，用户的全局 guard 一律拦。
- **流量控制**：事先定一个上限（比如最多 5 个开着的 PR）。到了就停，不再往上叠——一早面对二十个 PR 和面对一个两千行的 PR 一样读不动。
- **每个 PR 都按 `pr` 模板写**，Evidence 里放这一步自己的 back-pressure 结果。最后一个 PR（或单独一条总结）写明整体跑到哪一步、哪一步停了、为什么。
- 走不通、做成了原型的那种（完成标准的第 1 种），不要硬切成一串：出一个 PR 加探路报告。

## 怎么跑：按活的形状选

| 活的形状 | 用什么 |
|---|---|
| 路没看清（有未知要撞） | 一个 agent 打通最薄的一条、真跑；或上面那种 workflow，重点在第一阶段 |
| 路清楚，几块之间有约定（大多数功能） | `.claude/skills/spec-to-impl/SKILL.md`（用户只审 spec，主会话派 subagent、看结果、合并）；或上面那种 workflow |
| 路清楚，十块以上互不相干，有机器能判的裁判（机械迁移、按规范重构、审计加修复） | dynamic workflow，可以一开始就并行 |

用不用 dynamic workflow 由用户当次说了算。区别在计划握在谁手里：派 subagent 时主会话看了结果再定下一步，中途能调整；workflow 的流程写死在脚本里，中途不能改、也不能问人，但结构上的保证（必须真跑、必须独立审）一定会执行，适合没人盯的夜里。

## PR 怎么写

用 matt 的 `pr` skill 的模板（Summary 用图或 diff 草图 / Evidence 前后对照 / Merge Danger）。lights-off 的 PR 另外写明：

- 属于上面两种里的哪一种。
- 探路发现：撞到的未知、走不通的路。
- 哪些部分可以留，哪些该重写，建议怎么拆成小 PR。
- 没验证的部分；花了多少。

## 不做的事

- 不合并，不部署生产，不动生产的资源。
- 不强制推送主干；功能分支上只用带租约的强推（`--force-with-lease`，写明远端和分支名），不用裸的 `--force`。
- 不把原型包装成可以直接合并的成品。

## 第二天

用户读 PR，判断是哪一种：

- **第 1 种**：把 insight 带进当天的开发（走 `docs/agents/dev-workflow.md` 的正常流程），原型留作参考，PR 关掉。
- **第 2 种**：agent 先自己过一遍质量，重写写得差的部分，再拆成几个小 PR（叠在一起、按顺序合，每个的 diff 只含自己那一步），用户逐个读，合并。
