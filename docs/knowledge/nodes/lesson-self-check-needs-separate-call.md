## 结论

**写作时的『覆盖检查』和『写一篇好稿』是两个不同的任务，塞进同一次调用会让前者输给
后者**。写作调用的主要目标是产出流畅、有分析深度的正文，覆盖检查只是众多约束之一；
在生成过程中，模型对『要不要多提一句某个次要信息点』的决策会被『这句话是否让稿件更好』
主导，而不是『这个信息点客观上该不该被覆盖』——这是一种隐式的、不透明的取舍，观察者
只能看到结果（漏了什么），看不到决策过程。把『检查覆盖』单独做成一次调用，让模型的
唯一任务就是『找出材料里有、稿件里没有的东西』，才能让这个判断摆脱『是否让稿件更好』
这个竞争性目标的干扰。

## 判断『这是不是合理取舍』的方法：排除替代解释，不要直接假设

观察到模型漏写了材料时，直觉上有两个最省事的解释：『篇幅写不下』和『模型在做合理的
编辑取舍』。这两个解释都可以用生成过程本身产生的、不需要额外标注的信号直接排除：

- **篇幅够不够**：看 `finish_reason` 是否为 `length`（被截断）以及输出 token 相对上限
  的占用比例。全部正常收尾（`stop`）且只用了不到两成预算，就排除了『写不下』。
- **是不是合理取舍**：看某个可独立度量的重要性指标（例如报道篇数）与是否被写入之间
  有没有对应关系。如果重要性高的内容采纳率也不高（本例核心事件采纳率仅 38–56%），
  就排除了『按重要性合理筛选』。

只有把这两个最容易被想到的解释都排除掉，『需要一个独立步骤补漏』这个更贵的结论
（需要多一次调用、多一份成本）才站得住——否则很容易在『可能只是篇幅问题』或
『模型的取舍其实没错』上打转，迟迟不引入额外机制。**这个排除替代解释的方法，比
『41.1%→51.9%』这个具体覆盖率数字更值得在其他场景复用**：任何观察到生成内容有遗漏
时，都可以先用现成的元数据信号（完成原因、长度用量、独立于生成过程的重要性排序）
挡掉『空间不够』和『合理筛选』这两个最常见的辩护，再决定要不要引入额外的检查步骤。

## 为什么不随架构死

『生成任务里的隐式约束会输给主要目标』是任何多目标生成场景的通用现象，不是新闻简报
写作专属——概括语言模型的注意力分配特性，而不是某一版 prompt 的具体表现。换任何模型、
换任何具体的『补漏』实现，这条关于『竞争性目标会互相压制』的机制预期仍然成立；会变的
只是压制的具体数字。

## 与其他补漏经验的关系（不合并、只对照）

本地会话记忆记录的『两遍法』修法（合成层漏报 13.4%→0%，先去编造再补漏，且补录内容不
经 LLM、程序化拼装）解决的是**故事级**遗漏（整份简报该收哪些候选故事），本条经验解决的
是**信息点级**遗漏（单个 story block 内该覆盖材料里的哪些点）。两者共享『生成与检查
分离、且顺序要先处理更严重的失真类问题再补遗漏』这一更高层的结构原则，但任务粒度、
实现代码、验证数据都不同，是该原则在两个层面各自独立验证的实例，不构成重复。
